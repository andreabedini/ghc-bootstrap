*2026-09-10. Result: **the compiler links, runs, and compiles 137 of the 143
modules of GHC 6.2.2's `libraries/base` to `.hi` + `.hc`**, and every one of those
`.hc` files compiles to `.o` with gcc against `build/rts622`'s headers. Five
runtime gaps were found and fixed; three modules remain open (one space
blow-up, two timeouts of the same shape), and four more need `hsc2hs`, which
does not exist in the chain yet.*

Directory `build/ghc622-mhs`. Scripts: `build.sh` (link), `run-base.sh`
(compile base), `build-hc.sh` (.hc -> .o), `comb2c.py`, `gen-htypes.c`,
`ghc622/tools/base-order.py`. Log: [`LOG.md`](LOG.md). Results: `base-results.tsv`.

## 1. The binary

| step | how | cost |
|---|---|---|
| `mhs ... Main -o ghc.comb` | `build.sh comb`, probe defines + `-i` flags, probe's `-C` cache copied to `./.mhscache` | 9 min |
| `comb2c.py ghc.comb ghc-data.c` | `build.sh c` | 2 s |
| `gcc ... -o ghc` | `build.sh cc`: MicroHs `main.c` + `eval.c` + `ghc-data.c` + `ffi.c` + `stubs.c` | 7 s |
| | | **2.9 MB `ghc`** |

- **Why the `.comb` detour.** `mhs -o ghc.c` does the same compile and then
  writes ~7.7 MB of C array; it needs ~13 min in one process, and the sandbox
  kills a foreground Bash call at 10 min and a background one under memory
  pressure. `mhs -o ghc.comb` writes the same `outData` (Main.hs:391 vs
  404-410) in a quarter of the text, and `comb2c.py` produces the byte array
  `makeCArray` would have (MakeCArray.hs:26-32). `build.sh hs` still does it
  the direct way if you have the time.
- **`ffi.c`** is the FFI table `mhs -o *.c* would have emitted. The closure's
  foreign imports are 185 names (`rg -o '\^&?\w+' ghc.comb`); all but four are
  in the MicroHs runtime's own `ffi_table` (eval.c:7861). The four are
  `rawSystem` (SysTools's private one, `__GLASGOW_HASKELL__ < 603` branch),
  `setHeapSize` and `enableTimingStats` (DriverFlags's RTS hooks) and `getpid`
  (the Posix shim, for `newTempName`). Each wrapper is exactly what mhs
  generates for that Haskell type, checked against `t/ft.c`.
- **`stubs.c`** defines those three C functions: `rawSystem` is the Unix branch
  of `libraries/base/cbits/rawSystem.c`; the two RTS hooks are no-ops under the
  MicroHs runtime.
- **`rtconf/config.h`** is MicroHs's `src/runtime/unix/config.h` with
  `WANT_OVERFLOW 0`, generated by `build.sh` and searched first. See gap 3
  below. MicroHs itself is not modified.

```
$ ./ghc -B$PWD/topdir --version
The Glorious Glasgow Haskell Compilation System, version 6.2.2
$ ./ghc -B$PWD/topdir --numeric-version
6.2.2
```
`-v` prints the banner, the package-config path and both packages, so the
lexer, `StringBuffer`, `ParsePkgConf` and `Packages` all run.

`<topdir>/package.conf`, `<topdir>/unlit`, `<topdir>/ghc-usage.txt`:

| entry | what |
|---|---|
| `package.conf` | hand-written: `rts` and `base`, "installed" layout, `$libdir` = topdir |
| `unlit` | `ghc/utils/unlit/unlit.c` compiled `-std=gnu89 -Wno-implicit-int -Wno-implicit-function-declaration -include string.h` (it is K&R C) |

`gcc -E -undef -traditional`, `as` and `ld` are gcc, `touch`/`cp` are the

unregisterised via-C route does not mangle or split.

`libraries/base/Makefile` + `mk/package.mk` + `mk/config.mk` prescribe
(`-fglasgow-exts -cpp -Iinclude -#include HsBase.h -funbox-strict-fields

`{-# SOURCE #-}` imports dropped, and an implicit `Prelude` edge for every
module without `-fno-implicit-prelude`.

**136 OK in the ordered pass** (`base-results.tsv`), plus `GHC.PrimopWrappers`
on retry = **137**. Every `.hi` is read back by later modules, so the
interface round trip works.

Six modules needed `-O -fno-strictness` (see gap 4): `GHC.Real`, `Numeric`,
`GHC.Handle`, `GHC.IO`, `Data.Typeable`, `Control.Concurrent.SampleVar`,

## 4. Every runtime gap found, with root cause and fix

**1. `exitWith` reported as "the impossible happened".** `DriverUtil.handle`
has `#if __GLASGOW_HASKELL__ < 501` = `flip catchAllIO`, which catches
everything, `#else` a version that re-throws `ExitException`. We compile with
`-D__GLASGOW_HASKELL__=408`, so the driver caught its own `exitWith` and
Main's `_other ->` arm turned every clean exit into a panic. Fixed by giving
the `EXCEPTION` shim the `ExitException ExitCode` constructor 4.08's hslibs
had (mapping MicroHs's `ExitCode` exception to it, and re-throwing the bare
`ExitCode` so the runtime exits with that code) and taking the `>= 501` branch
under `__MHS__`.

**2. `hFileSize: not available in MicroHs`.** `Binary.readBinMem` sizes the
interface file with `hFileSize`; MicroHs handles cannot report a size. It has
the path, so the `__MHS__` branch reads the file with `readBinaryFile` (binary
mode, no utf8 layer) and takes `length`. Without this no interface could be
read at all.

**3. Trapping `Int` overflow.** MicroHs's unix config sets `WANT_OVERFLOW 1`,
so `+`, `-`, `*` on `Int` *raise* where GHC wraps. `CoreUtils.hash_expr`
multiplies hashes until they wrap on purpose, so CSE died on every module at
`-O`. Fixed by compiling the binary against `rtconf/config.h`
(`WANT_OVERFLOW 0`), generated from MicroHs's own file at build time.

**4. Checked narrowing into `Int8`/`Int16`/`Int32`.** `fromInteger` into those
types raises `_overflowError` (`Data/Int/Int8.hs:32`) instead of wrapping
modulo 2^n. `Binary Integer` writes the sign of a negative number as an
`Int8` 0xff, so *every negative literal in an interface* -- `minInt` in
`GHC.Base`, hence `GHC.Enum` -- crashed the importer the moment the unfolding
was demanded: only at `-O`, and only with an `-O`-built `.hi`. Fixed in
`Binary.hs` (`mhsSigned` + the three `Binary IntN` instances) and, before it
could bite, in `Literal.lhs`, whose `narrow8IntLit`/... folded the narrowing
primops through the same checked conversions (now `narrowSigned`/
`narrowUnsigned`, done in `Integer`).

**5. `negate`/`abs` of `minBound`.** `eval.c:6592` checks `T_NEG`
unconditionally -- `WANT_OVERFLOW=0` does not disable it -- so `abs minBound`
raises where GHC returns `minBound`. `CoreUtils.hashExpr` did exactly that
(with a guard for the negative result it expected). Rewritten to test for
`minBound` first.

**6. The demand analyser exhausts the stack, then the heap.** `GHC.Arr` and
`GHC.Real` died in `*** Demand analysis:` with the runtime's own
`ERR: stack overflow` (default stack 250000 slots). `+RTS -K5M` turns it into
`ERR: heap exhausted`; `-K50M -H100M` (1.6 GB) still exhausts it after 465 s.
`-O -fno-strictness` compiles `GHC.Arr` in 19 s. `dmdFix.loop`
(`DmdAnal.lhs:355-395`) accumulates `plusUFM_C both` thunks across up to ten
iterations; GHC's own strictness analysis kept those chains short when GHC
compiled itself, and mhs preserves the laziness literally. `run-base.sh`
retries once with `-fno-strictness` when it sees either message.

**7. `HTYPE_INT` not in scope** (`Foreign.Storable`, and 96 modules behind it).
Not a compiler bug: configure's `FPTOOLS_CHECK_HTYPE` probes compile a program
whose `main() {...}` has no return type, which gcc >= 14 rejects, so the 6.2.2
configure run left every `HTYPE_*` as `#undef` -- the same 2026-toolchain class
as [D31](../../DECISIONS.md#d31--run-ghcs-own-configure-instead-of-hand-writing-configh)/D40. `gen-htypes.c` reruns the probes' logic verbatim; its 34 defines
are appended to `build/ghc-6.2.2-run1/ghc/includes/config.h`.

Also worth recording, though neither is a bug:
- The MicroHs runtime's `+RTS -K5M -RTS` is consumed by the runtime, not the
  driver, so it can be passed straight through on the `ghc` command line.
- `run-base.sh` runs with `ulimit -s unlimited`; without it the evaluator
  segfaults instead of reporting a stack overflow.

## 5. The RTS accepts the output

`build-hc.sh` compiles every produced `.hc` with the flags
`build/rts622/build-rts.sh` uses for the RTS's own `.hc` files:

```
gcc -c -x c -std=gnu89 -O -w -DNO_REGS -DUSE_MINIINTERPRETER \
    -D__GLASGOW_HASKELL__=622 -I<our ghc/includes> -Iinclude -I. \
    -include <our ghc/includes>/Stg.h  X.hc -o hcobj/X.o
```

(`-Iinclude` for base's headers, `-I.` for the `Control/Concurrent_stub.h`
that the driver itself emitted alongside `Concurrent_stub.c`, which the driver
also compiled.)

**137/137 objects, no errors.** `GHC/Base.o` defines
563 global symbols and leaves 17 undefined; 15 of them are in
`build/rts622/libHSrts.a` (`stg_ap_*_info`/`_ret`, `stg_upd_frame_info`,
`stg_seq_frame_info`, `stg_CAF_BLACKHOLE_info`, `stg_IND_STATIC_info`,
`stg_gc_unbx_r1`, `stg_gc_ut`, `newCAF`, `MainCapability`, `gcdIntzh_fast`)
and 2 are base's own (`GHCziErr_error_closure`, `__stginit_GHCziErr_`).

So [D45](../../DECISIONS.md#d45--d44-overturned-the-entry-point-moves-to-ghc-622)'s second "not yet shown" -- that the compiler proper's
`Constants`/`Config` for an x86-64 target produce `.hc` files this RTS accepts
-- is shown at the level of compilation and symbol agreement. A full link of a
program was **not** attempted: it needs every module of base (three are still
missing), the `.hsc` four, base's `cbits`, and `libHSbase.a`; the first
missing piece is `hsc2hs`.
